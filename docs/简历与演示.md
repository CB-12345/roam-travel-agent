# 简历与演示

## 项目定位

ROAM 漫游：基于公开源码旅行助手二次开发的多智能体旅行工作台。适合展示 AI 应用开发、业务约束、工具落地、交互和可靠性。保留上游归属，不把复现部分全部描述为从零研发。直接上游许可尚待明确，见 [来源声明](../NOTICE.md)。

## 可按实际贡献改写的简历条目

**ROAM 多智能体旅行规划工作台｜Python、FastAPI、LangChain、Pydantic、SQLite、SSE、JavaScript**

- 基于现有项目改造旅行规划链路，通过景点、天气、酒店研究 Agent 并行收集资料，结合规划 Agent 形成每日安排；将模型选择约束在工具候选池中，接入高德 POI 与和风天气。
- 实现指定日期的对话修改、真实候选替换、地点锁定和最近五次撤销；修改后统一核对交通耗时、完整游玩时长、三餐窗口、常规开放时间及费用账目，失败保留原版本。
- 将后台任务落盘 SQLite，使用幂等提交、有序 SSE 重放和快照补偿支持刷新取回结果；增加分级质量检查、调用耗时与提供方 Token 统计、JSON 备份导入及无需 Key 的历史示例。
- 建立离线单元/接口回归测试与 20 个录制行程故障注入案例，提供可执行评测脚本及 CI 配置；具体测试结果见 README 与评测文件。

以上是本地已实现能力的写法。只有自己理解、复现并能解释对应模块后再写进简历。不要写“生产高并发”“大规模真实用户”“准确率提升 xx%”“实时酒店预订”等没有证据的指标；当前用量记录也不能直接换算通用成本。

## 3–5 分钟演示

1. 首页点击“查看示例行程”，解释其日期和历史数据标识。展示照片、具体地址、高德入口、每日安排和预算；打开行程检查，说明为何复杂开放规则仍待确认。
2. 返回“调整需求”，选 1 日城市旅行并生成。规划时刷新页面，展示取回同一任务而非再次调用模型。
3. 进入真实生成行程，锁定一个景点，再通过对话调整某一天的需求，展示变更对比。解释锁定保留地点和日期，时间仍可变化。
4. 点击“换一个”，比较有真实地址的候选，再确认替换。展示预算同步和撤销。
5. 备份 JSON、导入为新行程；打开折叠的数据来源与运行统计。最后展示 `pytest` 与离线评测结果。

实时模型和第三方接口可能波动，演示前先跑一遍；没有 Key 时使用只读示例，明确说明未进行实时规划。样例仅帮助展示界面，不是在线模型评测。

## 面试应能讲清的点

**为什么需要多个 Agent？** 景点、天气、酒店具有独立工具与数据约束，可以并行研究、分别维护输入输出；骨架与每日编排依赖研究结果。不要声称多 Agent 天然提高准确率，效果需要评测。

**怎样减少幻觉？** 用候选白名单和身份匹配约束实体，真实餐厅需要检索落地；模型负责表达与选择，后端核对时空与账目。缺失资料明确显示未知。

**为什么通用助手不能完全代替？** 优势来自可编辑的持续行程状态、地点和日期锁定、交通/营业/预算的执行规则与透明资料来源。模型能力仍可被其他模型替换，项目并不存在无法复制的技术壁垒。

**如何处理模型输出错误？** 结构化校验、候选验真、独立规则验收、事务式修改及撤销。工具或模型失败不会自动把原行程覆盖成半成品。

**刷新恢复到了哪一层？** 服务端任务继续执行，客户端恢复其结果；重启进程会明确终止未完成任务，不是从模型内部 checkpoint 继续。幂等保护应用提交，SDK 自己的重试另有边界。

**为什么只使用单 worker？** 当前规划器维护请求期可变上下文，串行任务避免串数据；单任务内部研究并行。要扩容需拆出独立上下文和共享任务调度，而不是直接增加 Uvicorn worker。

**评测的 20/20 说明什么？** 一份录制行程加确定性异常注入均符合预期，证明这些规则回归没有破坏；它不表示 100% 规划正确，也没有覆盖全国所有城市。

**真实接口测了什么？** 已测杭州、成都、北京和广州四种需求，包含低预算、远期天气与局部修改；首次杭州早餐门店营业时间冲突被拦截，修正候选筛选后复测通过，保留失败记录。见 [验证记录](验证记录.md)。这仍只是少量工程样例；进一步需要人工标注可行性与用户满意度，再测成功率、延迟分位数和修改保留率。
